# Agent、Skill 与 Workspace 的职责

## 当前组织方向

当前认可的方向是：使用一个具有教学主导权的 Architecture Mentor（架构导师）进行上层编排，必要时组合多个围绕认知动作设计的 Skill（技能模块），由 Workspace（工作区）提供长期、可追溯的学习状态，并由 Mentoring Contract（导师契约）提供用户拥有的目标和权限边界。

这是一种职责模型，不是已经确定的进程架构或文件目录。Agent 数量、Skill 数量、名称和具体存储结构仍待设计。

## 三层职责

| 组成 | 核心问题 | 主要职责 | 不应承担的职责 |
| --- | --- | --- | --- |
| Architecture Mentor（架构导师） | 现在为什么要做什么？ | 观察表现、提出诊断假设、确定学习优先级、选择策略、调整挑战难度、根据新证据改向 | 把诊断当事实；替学习者长期完成关键推理；把所有策略实现塞进一个大提示词 |
| Skill（技能模块） | 选定策略后怎样高质量执行？ | 提供某类认知工作的执行方法、证据要求、质量检查和可复用工具 | 按知识章节接管长期课程；自行决定学习者的最终目标；维护彼此冲突的学习者状态 |
| Mentoring Contract（导师契约） | 系统当前服务于什么目标和边界？ | 保存用户确认的目标、现实约束、导师权限和否决边界 | 被导师根据推断静默修改；与学习者模型混为一体 |
| Workspace（工作区） | 导师凭什么形成当前判断？ | 保存原始历史及五类长期记忆，维护来源、证据链、生命周期、替代关系和活跃工作集 | 把全部历史直接注入上下文；把导师评价伪装成证据；用一个文件混放所有类型信息 |

## Skill 应围绕认知动作拆分

不建议优先按知识领域拆成：

```text
DDD Skill
Distributed Systems Skill
AI Architecture Skill
Data Skill
```

这种结构容易退化成课程章节，也会让多个 Skill 重复承担诊断、教学和状态维护职责。

更合适的候选拆分维度是学习动作，例如：

- 调查一个陌生系统；
- 重建一项架构决策及其约束；
- 挑战一个设计；
- 比较两个架构；
- 分析事故与失败模式；
- 从项目经历中提炼经验；
- 构造反例或反事实；
- 验证能力迁移；
- 维护和校准学习状态。

这些只是候选模块，不代表已经确定必须实现九个 Skill。确认的是拆分原则：Skill 围绕“怎样完成一种认知工作”组织，而不是围绕“教授哪一章知识”组织。

## 依赖方向

三层之间的依赖应保持单向清晰：

```text
Architecture Mentor
  ├─ 读取当前 Mentoring Contract
  ├─ 读取经过筛选的学习状态
  ├─ 选择一个适合当前目标的策略
  └─ 调用对应 Skill 执行

Skill
  ├─ 读取完成当前任务所需的证据
  ├─ 产出观察、推断、挑战或验证结果
  └─ 提交候选 Experience / Evidence / Insight，
     不直接宣布永久能力结论

Workspace
  ├─ 保存来源、历史和五类长期记忆
  ├─ 维护证据链、生命周期和替代关系
  ├─ 控制 Active Memory 工作集
  └─ 按需检索归档内容
```

用户通过 Mentoring Contract 持有目标和边界，导师负责策略选择，Skill 负责策略执行，Workspace 负责状态依据。这个边界用于防止系统演变成一个职责混杂的“大 Skill”。

当导师或 Skill 准备写入长期 Evidence、提升 Capability State 或修改 Mentoring Contract 时，必须触发 [《长期状态变更门禁》](./state-change-gates.md)。其他教学动作默认不经过统一流程。

在上述责任边界上已经进一步推导出两份 v1 逻辑设计：

- [《Workspace 目录设计》](./workspace-directory-design.md)：定义契约、历史、五类记忆、导师运行记录和派生视图的逻辑分区；
- [《Skill 职责设计》](./skill-responsibility-design.md)：定义策略执行与状态维护职责、候选输出及长期状态写权限。

两份文档均不表示已经创建实际 Workspace 或 Skill，也不锁定最终存储介质和物理模块数量。

## 下一阶段应先解决的问题

目前已经有了五类记录、证据阶梯和生命周期的第一版语义。下一步不应直接猜测目录树，而应继续把语义具体化为：

1. Experience、Evidence、Hypothesis、Capability State 和 Architecture Insight 的记录模板；
2. 五类记录之间使用什么标识符和引用方式保持可追溯；
3. Mentoring Contract 的具体结构以及学习、交付、混合模式的切换规则；
4. 三类门禁由导师、独立校验器还是二者共同执行；
5. 候选转为活跃、能力阶段升级或进入受质疑状态所需的证据阈值；
6. Active Memory 的容量预算、排序和按需检索规则；
7. 导师如何在学习者兴趣、现实交付要求、长期能力地图和当前证据之间确定优先级；
8. 哪些更新由 Skill 提交候选，哪些只能由上层导师校准后写入。

这些约束确定之后，Workspace 目录、存储介质、Agent 提示词和 Skill 边界才有稳定依据。即使未来从 Markdown 文件切换到数据库，Memory Model 本身也不应依赖具体存储方式。
