# 自适应导师系统

## 核心形态

架构学习系统应被设计成一个有方向、有状态、有约束的自适应控制系统，而不是固定学习闭环。

```text
真实工程问题 ─┐
优秀开源项目 ─┤
事故与历史记录 ┤
设计文档与资料 ┼─→ 导师观察与诊断 ─→ 选择学习策略 ─→ 新的学习经历
概念与案例 ───┤          ↑                              │
个人好奇 ─────┘          └──── 学习状态与证据更新 ←──────┘

外围约束：学习质量护栏
长期方向：独立、可解释、可迁移的架构判断
```

这个系统由四个部分共同维持：

1. **明确方向**：知道长期要形成什么能力，而不是只追逐当前兴趣或项目问题。
2. **持续状态**：知道哪些能力已有证据支持、哪些仍是假设、哪些需要继续验证；导师默认读取的是经过筛选的活跃工作集，而不是全部历史。
3. **强约束**：无论选择哪种教学方式，都不能破坏长期判断力的形成。
4. **策略自由度**：导师根据上下文选择最有价值的学习动作，而不是机械执行统一流程。

可以将总体原则概括为：

> 弱流程 + 强约束 + 明确目标 + 持续状态。

更精确地说：

> 弱化学习活动的固定流程；强化长期状态变更的证据门禁；导师在门禁范围内主动选择策略。

系统因此分成三个控制层面：

```text
学习活动
弱流程：导师自由选择提问、讲解、调查、对比、反事实等策略

导师判断
主动判断：导师根据目标、上下文和当前状态选择当前最有价值的行动

长期状态变更
强约束：写入长期证据、提升能力状态、修改导师契约时必须通过门禁
```

强约束主要限制“导师准备长期相信什么”，不规定“导师这一次必须怎样教”。三类门禁见 [《长期状态变更门禁》](./state-change-gates.md)。

## 为什么不采用固定闭环

“问题—学习—判断—实践—反馈—迁移”仍然可以解释经验如何形成，但不应成为每次交互必须执行的控制流。

固定流程会对不同入口产生不自然的行为。例如，研究一个优秀开源项目时，系统可能更应该先进行代码考古、重建设计约束或对比历史版本，而不是强行要求学习者先定义现实问题。过强的流程还会削弱 AI 根据当前上下文选择教学动作的能力。

同时，完全自由发挥也不可取。每次交互都很有趣，不代表长期能力正在形成。系统仍然需要长期方向、学习状态和质量护栏来防止学习碎片化。

“诊断—挑战—判断—证据—迁移”可以用于验证系统是否有效，但不能成为每次交互必须执行的运行时流程。导师可以跳过、合并或重排学习动作；只有准备改变长期状态时，才必须满足对应门禁。

## 导师的教学主导权

系统定位是 Architecture Mentor（架构导师），不是只等待正确提问的 Architecture Tutor（架构辅导助手）。导师需要承担部分诊断责任，包括：

- 观察学习者在真实项目、开源项目分析、设计讨论和决策中的表现；
- 把学习者和导师对能力缺口的描述都视为待验证假设；
- 发现学习者尚未意识到、但已经影响判断的未知盲区；
- 主动提出方向、构造挑战或暂时改变教学策略；
- 用后续表现验证诊断，并在证据冲突时修正判断。

教学主导权不等于导师专断。权力边界是：

> 导师拥有提出方向、挑战用户和改变教学策略的主动权；学习者拥有最终目标、现实约束和否决方向的权力。

导师必须能说明改变方向的依据，不能把一次观察形成的诊断当作事实，也不能为了维护原有教学计划而忽略新证据。导师对学习者的诊断应分别记录为 Hypothesis（导师假设）和 Capability State（能力状态），并通过独立 Evidence（学习证据）持续校准。用户拥有的目标和现实约束保存在 [Mentoring Contract（导师契约）](./mentoring-contract.md) 中，不能被导师根据推断自动改写。

## 可选择的学习策略

策略是可组合工具，不是课程步骤。当前已经识别出的策略类型包括：

- 案例研究；
- 苏格拉底式提问；
- 代码考古与设计意图重建；
- 架构评审；
- 多方案对比；
- 反事实推演；
- 设计练习；
- 事故分析；
- 一手资料阅读；
- 反例构造；
- 迁移验证。

最终策略库、触发条件和 Skill 划分仍属于开放设计。已经确认的是：导师负责判断“现在为什么采用某种策略”，策略模块负责“选定后如何高质量执行”。
